Product Requirements Document (PRD)
Система распознавания лиц и мониторинга здоровья для школы
Версия: 1.0
Дата: 31.03.2025
Автор: Олег Чекмарев

1. Введение
1.1. Цель документа
Определить функциональные и нефункциональные требования для веб-приложения, которое:
•Фиксирует лицо человека с камеры/фото.
•Распознает личность, сравнивая с базой данных.
•Определяет признаки болезни (например, повышенная температура, усталость).
•Отправляет уведомление охране, если:
•Человек не найден в базе (неавторизованный доступ).
•Обнаружены признаки болезни.
1.2. Целевая аудитория
•Школьная администрация (безопасность, контроль доступа).
•Охрана (получение уведомлений о подозрительных лицах).
•Учителя и ученики (косвенные пользователи).
2. Обзор продукта
2.1. Основные возможности
✅ Распознавание лиц (сравнение с базой данных).
✅ Классификация состояния здоровья (признаки болезни).
✅ Автоматические уведомления охране (Telegram-бот).
✅ Веб-интерфейс (простое взаимодействие).
2.2. Технологический стек
- Фронтенд: Next.js (TSX), Tailwind CSS, shadcn/ui
- Бэкенд: Supabase (PostgreSQL)
- Аутентификация: NextAuth.js
- Хостинг: Vercel
- Уведомления	Telegram Bot API


3. Функциональные требования
3.1. Основные сценарии использования
Сценарий 1: Распознавание авторизованного лица
1.Пользователь подходит к камере.
2.Система делает фото и извлекает эмбеддинг лица.
3.Сравнивает с базой данных.
4.Если совпадение найдено → доступ разрешен.
Сценарий 2: Обнаружение незнакомца
1.Лицо не найдено в базе данных.
2.Система отправляет уведомление охране:
•Фото человека.
•Время обнаружения.
Сценарий 3: Обнаружение признаков болезни
1.Система анализирует лицо (температура, покраснение глаз и т. д.).
2.Если модель классифицирует состояние как "больной" → уведомление охране.
3.2. Дополнительные функции
•Журнал событий (логирование всех проверок).
•Ручное добавление лиц (админ-панель для загрузки новых фото).
•Тестовый режим (без отправки уведомлений).

4. Нефункциональные требования
4.1. Производительность
•Время обработки одного кадра: < 2 секунды.
•Поддержка 10+ одновременных запросов (для Heroku Free Tier).
4.2. Безопасность
•Локальное хранение данных (SQLite, без облачных утечек).
•Шифрование уведомлений (Telegram использует MTProto).
4.3. Масштабируемость
•Возможность замены SQLite на PostgreSQL при росте данных.
•Модульная архитектура (можно заменить модель классификации).

5. Ограничения
⚠ Точность распознавания зависит от освещения и качества камеры.
⚠ Модель "болезни" требует дообучения на реальных данных.
⚠ Бесплатные хостинги (Heroku, PythonAnywhere) могут иметь лимиты.

6. Метрики успеха
📌 90% точность распознавания известных лиц.
📌 Ложные срабатывания < 5% (для уведомлений).
📌 Охранник получает уведомление в течение 10 секунд.
